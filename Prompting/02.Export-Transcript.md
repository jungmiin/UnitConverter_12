### 3) 성공 기준 3개 (Mom Test 증거와 연결)

1. **단위 추가 시 수정 지점이 한 흐름으로 모인다**
   - *증거:* "inch 하나 넣으려면 최소 세 군데(elif, meter 환산, 출력)"
   - *성공:* 새 단위(예: inch) 추가 시 `elif`·출력 블록·비율 상수를 **각각 따로** 늘리지 않고, 단위/비율 정의 **한 경로**만 바꿔도 인식·환산·출력이 맞다.

2. **입력 분기와 출력 계산이 어긋나지 않는다**
   - *증거:* "feet 쪽 elif만 고치다가 출력의 in_feet 곱셈을 안 맞추면 불일치"
   - *성공:* feet(또는 임의 단위) 비율을 바꿔도 **입력으로 받은 단위 → meter → 다른 단위** 결과가 **같은 비율 정의**에서 나와, 한쪽만 수정해도 테스트가 실패한다.

3. **수동 실행 없이 회귀를 잡을 수 있다**
   - *증거:* "자동 테스트가 없으면 `python UnitConverter.py`로 meter:2.5, feet:10, 잘못된 입력을 직접 넣어봐야 한다"
   - *성공:* `meter:2.5`·`feet:10`·잘못된 형식·없는 단위 등 **Mom Test에서 손으로 확인하던 케이스**가 테스트로 고정되고, 리팩토링·단위 추가 후 **한 번의 테스트 실행**으로 다른 단위 결과 틀림을 알 수 있다.

---

### 4) 표면 문제 — 이번 프로젝트에서 하지 않을 것

README 추가 요구사항(신규 단위, 출력 포맷, 설정에서 비율 로드, 런타임 단위 등록)을 **"기능을 하나씩 붙이는 구현 과제"**로만 잡고, 그때마다 `main()` 안 **elif 분기·print 출력·하드코딩 비율을 계속 늘리는 것**.

구체적으로 하지 않을 것:

- inch 등 단위를 **elif + 출력 print + 상수** 세 군데에 또 복붙하는 방식으로만 추가하기
- JSON/CSV/표 출력·설정 파일·동적 등록을 **main() 분기와 print에 직접** 얹기
- "기능은 다 붙였다"고 보고 **자동 테스트 없이** `python UnitConverter.py` 수동 확인으로만 마무리하기
- OCP/SRP를 **주석이나 클래스 이름만**으로 충족했다고 보고, **변경 지점 수·회귀 검증**은 그대로 두기
