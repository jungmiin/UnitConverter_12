**1. 처음 코드를 봤을 때, 어떤 부분부터 이해하려고 했나요?**

`main()` 하나뿐이라 진입점부터 읽었다. 흐름은 단순했다: 입력 → `:` 분리 → `float` 변환 → `if/elif`로 meter 환산 → 세 줄 `print`. 다만 "변환 규칙이 어디에 정의돼 있는지"를 찾으려다 보니 함수 본문 전체를 다시 훑어야 했다. 클래스나 모듈 경계가 없어서, 구조도와 데이터 흐름을 그리기 전에 37줄 전체를 한 번에 읽는 수밖에 없었다.

**2. 새 단위를 추가하려고 했을 때 실제로 어느 부분을 수정해야 했나요?**

최소 세 군데다.

- 입력 단위 인식: `elif unit == "feet"` 블록 옆에 새 분기 추가 (16–24행)
- meter 환산: 해당 분기 안에 나눗셈 비율 추가 (18–21행)
- 출력: `in_feet`, `in_yards` 계산 블록에 새 변수 추가하고 `print` 한 줄 더 추가 (26–32행)

비율 상수 `3.28084`, `1.09361`도 입력 분기와 출력 계산에 각각 들어가 있어서, 새 단위 비율을 한 곳에만 넣을 수 없다.

**3. 단위 변환 비율을 바꾸거나 추가할 때 기존 코드 수정 범위가 어느 정도였나요?**

기존 단위 비율을 바꾸면 해당 `elif`의 나눗셈(18–21행)과 출력 쪽 곱셈(27–28행) **둘 다** 수정해야 한다. feet 비율을 바꾸면 `elif unit == "feet"`와 `in_feet = meter_value * 3.28084` 두 곳을 맞춰야 한다. 새 단위 추가면 분기 1곳 + 출력 변수 1곳 + `print` 1줄이 최소이고, 비율 상수가 코드에 6번(입력 3 + 출력 3) 흩어져 있어서 누락·불일치 위험이 있다.

**4. 기존 변환 로직을 수정하면서 다른 단위 변환이 깨질까 봐 걱정된 적이 있었나요?**

있다. meter 환산과 출력 계산이 같은 `main()` 안에 있고, 비율이 하드코딩·중복돼 있다. feet 쪽 `elif`만 고치다가 출력의 `in_feet` 곱셈을 안 맞추면, 입력은 feet인데 출력만 틀어지는 식의 불일치가 난다. 테스트가 없어서 "다른 단위는 괜찮은지"를 코드 리뷰와 수동 실행으로만 확인해야 했다.

**5. inch나 mile을 추가할 때, 기존 구조에서 가장 불편한 점은 무엇이었나요?**

단위마다 `elif`와 `print`를 복붙해야 한다는 점이다. 지원 단위가 늘수록 분기 수와 출력 줄 수가 같이 늘어난다. inch를 입력으로 받으려면 분기 추가, 출력에는 meter/feet/yard/inch/mile 전부 찍어야 해서 출력 블록도 계속 길어진다. "한 단위만 추가"가 아니라 `main()` 전체를 다시 읽고 여러 군데를 일관되게 맞춰야 한다.

**6. 입력 파싱, 변환 계산, 출력 formatting이 분리되어 있다고 느꼈나요?**

섞여 있다. `split(':', 1)`, `float()`, `if/elif` 환산, `print(f"...")`가 한 함수에 순서대로 붙어 있다. 파일·함수 이름으로도 Parser/Converter/Formatter 구분이 없다.

**7. 책임이 섞여 있어서 테스트하기 어렵다고 느낀 부분이 있었나요?**

`main()` 전체다. `input()`과 `print()`가 변환 로직과 붙어 있어서, "feet 10 → meter 값이 X"만 검증하려 해도 CLI를 흉내 내거나 `main()`을 통째로 실행해야 한다. 파싱 실패·숫자 오류·unknown unit도 `print` 후 `return`이라, assertion을 문자열·종료 방식에 묶기 쉽다. 변환만 단위 테스트하기 어렵다.

**8. 입력값 검증을 추가하려고 했을 때, 어디에 넣어야 할지 바로 판단됐나요?**

형식(`:` 없음)과 숫자(`ValueError`)는 이미 `main()` 앞부분에 있다. 음수 검증을 넣을 자리는 대략 `float` 성공 직후(11–14행 다음)로 보였지만, "검증 전용 레이어"가 없어서 `main()` 안 어디에든 `if value < 0`를 끼워 넣는 수준이다. 형식 검증과 단위 검증(22–24행)이 서로 다른 위치에 있어서, 검증 규칙이 늘면 `main()`이 더 길어지고 순서를 스스로 정해야 한다.

**9. 음수, 잘못된 형식, 없는 단위 오류 처리를 추가할 때 기존 코드가 방해된 부분이 있었나요?**

형식·숫자·단위마다 `print` 메시지와 `return` 패턴이 반복된다. 오류 종류가 늘수록 `main()` 상단이 `if print return` 나열로 비대해진다. 메시지 문구를 README나 AC와 맞춰야 하는데, 그게 변환 로직과 같은 함수에 있어서 오류 처리 수정 시 변환 코드까지 같이 보게 된다. 음수는 아예 없어서, 넣을 때 기존 분기 스타일을 따라야 하는지 별도 검증 블록을 둘지부터 판단 비용이 든다.

**10. 출력 포맷을 JSON/CSV/table로 나누려면 어떤 부분이 가장 많이 바뀔 것 같았나요?**

26–32행의 `print` 블록이 전부다. 지금은 줄 단위 문자열이 하드코딩돼 있어서, 포맷 분기를 넣으려면 이 구간을 통째로 갈아엎거나 `main()` 안에 `if format == 'json'` 같은 분기가 늘어난다. 입력·변환(4–28행)도 건드릴 수 있지만, 변경 폭은 출력 쪽이 가장 크다.

**11. 설정 파일에서 변환 비율을 로드할 때, 기존 구조가 자연스럽게 받아줄 수 있다고 느꼈나요?**

아니다. 비율이 `main()` 본문에 리터럴로 박혀 있고, 단위 목록이 `if/elif` 문자열에 고정돼 있다. 설정을 읽어도 넣을 그릇(단위 레지스트리, 비율 맵)이 없어서, 로더를 "붙이는" 게 아니라 환산·출력 흐름을 먼저 재구성해야 한다.

**12. 동적 단위 등록을 기존 코드 변경 없이 가능하다고 느꼈나요?**

불가능에 가깝다. 단위가 `"feet"`, `"yard"` 등으로 코드에 박혀 있고, 출력 대상도 `in_meters`, `in_feet`, `in_yards`로 고정이다. 런타임에 `cubit`을 등록하려면 분기 구조와 출력 루프 자체를 바꿔야 한다.

**13. OCP를 위반한다고 느낀 구체적인 지점이 있었나요?**

- 16–24행: 새 단위마다 `elif` 수정 — 확장 시 기존 분기를 열어야 함
- 26–32행: 출력 대상이 코드에 열거 — 새 단위마다 변수·`print` 추가
- 비율 변경도 기존 줄 수정 — 설정만 바꿔서는 안 됨

README "새 단위 추가 시 기존 코드 변경 최소화"와 맞지 않는다.

**14. SRP를 위반한다고 느낀 구체적인 지점이 있었나요?**

`main()`이 한 함수에서: 사용자 입력 수집, `unit:value` 파싱, 숫자·형식 검증, 단위 인식, meter 기준 환산, 전 단위 결과 계산, 콘솔 출력을 모두 한다. Parser / Converter / Formatter / (미래) Config Loader 중 어느 것도 단일 책임으로 분리돼 있지 않다.

**15. 테스트 코드를 작성하려고 했을 때, 어떤 함수나 동작부터 테스트해야 할지 명확했나요?**

아니다. 테스트할 함수가 없다. `main()`만 있고 변환은 그 안 인라인이다. 우선순위를 정하려면 "변환 정확도 / 입력 검증 / 출력 형식" 중 뭘 고정할지부터 정해야 하는데, 코드가 그 경계를 주지 않는다. README는 변환 정확도와 입력 검증을 요구하지만, 코드 구조상 어디를 먼저 뽑아낼지는 열려 있다.

**16. 변환 로직 테스트와 CLI 입출력 테스트를 분리하기 쉬웠나요?**

어렵다. 변환 로직이 독립 함수가 아니고 `input()`·`print()`가 `main()`에 직접 있다. 분리하려면 먼저 리팩토링으로 로직을 빼야 하고, 그 전에는 subprocess나 `input`/`print` mock으로 `main()` 통합 테스트만 가능하다.

**17. 기존 코드 수정 후 정상 동작을 확인하려면 매번 수동 실행이 필요했나요?**

자동 테스트가 없으면 그렇다. `python UnitConverter.py`로 `meter:2.5`, `feet:10`, 잘못된 입력 등을 직접 넣어봐야 한다. 비율이나 출력 한 줄을 고칠 때마다 눈으로 세 줄 출력을 확인하는 수밖에 없었다.

**18. 테스트가 부족해서 리팩토링을 망설인 적이 있었나요?**

망설일 만하다. Parser/Converter/Formatter로 쪼개면 동작은 같아야 하는데, 고정할 테스트가 없다. 출력 문자열(`2.5 meter = 8.2 feet` 형식, 소수 표기)이나 에러 메시지 전문이 바뀌었는지 검출할 안전망이 없어서, 리팩토링 후 회귀를 수동에 의존한다.

**19. 리팩토링을 한다면 가장 먼저 분리해야 한다고 느낀 책임은 무엇이었나요?**

**변환 계산(meter 기준 환산 + 다른 단위로의 수치 계산)**이다. 지금 가장 비즈니스 핵심이고, `elif`와 출력 곱셈에 이중으로 들어가 있어서 단위·비율 변경 때마다 가장 자주·위험하게 건드리는 부분이다. 여기가 독립되지 않으면 파싱·포맷·설정을 아무리 나눠도 "숫자가 맞는지" 검증 비용이 줄지 않는다.

**20. 이 코드가 유지보수하기 좋아졌다고 판단하려면 어떤 변화가 보여야 하나요?**

- 새 단위 추가 시 `main()`의 `if/elif`·`print` 나열을 늘리지 않아도 되는지
- 비율 변경이 한 곳(설정 또는 단위 정의)에서 끝나는지
- 변환·파싱·포맷 각각 단위 테스트가 있고, `main()` 수정 없이 통과하는지
- JSON/CSV 같은 출력 추가가 Formatter 쪽 변경으로 끝나는지
- 수동 실행 없이 `pytest` 한 번으로 기존 `meter:2.5` 출력과 에러 메시지가 고정되는지

이게 보이기 전까지는 "구조 개선됐다"고 말하기 어렵다.

**21. 새 단위 추가 시 기존 코드를 거의 건드리지 않아도 된다면, 어떤 부분에서 시간이 줄어들 것 같나요?**

- `main()` 전체를 다시 읽으며 분기·출력 줄을 맞추는 시간
- 비율을 입력·출력 두 곳에 넣다 하나 빠뜨리는 디버깅 시간
- 기존 meter/feet/yard 동작이 깨졌는지 수동으로 돌려보는 시간
- "어디까지 수정해야 하지?"를 매번 37줄에서 찾는 판단 비용

등록·설정 한 줄 추가로 끝나면, 대부분 여기서 줄어든다.

**22. 단순 기능 구현보다 설계 개선이 중요하다고 느낀 이유가 있었나요?**

README가 OCP·SRP를 품질 요구로 명시하고, 추가 요구(설정 로드, 동적 등록, 출력 포맷)가 이미 있다. 지금 구조로는 inch 하나도 `main()` 다발 수정인데, 설정·동적 등록·JSON까지 같은 방식으로 붙이면 `main()`이 한 파일에 다 쌓인다. 기능만 얹으면 단기적으로 돌아가도, 다음 요구마다 수정 범위와 회귀 위험이 같이 커진다. 요구 목록 자체가 "한 번에 많이 바꿔야 하는 구조"를 전제로 한다.

**23. AI에게 이 코드를 수정시키면 과하게 한 번에 바꿔버릴 위험이 어디에 있다고 느꼈나요?**

- 클래스·모듈·인터페이스를 한 diff에 다 도입해 37줄이 여러 파일로 갈아엎기
- stdout 문자열·에러 메시지까지 "개선"해 README/AC와 어긋나는 출력
- 설정 JSON, 동적 등록, 포맷 선택을 Mom Test·테스트 없이 한꺼번에 구현
- 테스트 없이 리팩토링만 해서 동작은 같아 보이는데 소수 표기나 줄 형식이 미묘하게 바뀜
- `input()`/`print()` 제거·시그니처 변경으로 기존 실행·확인 방식과 계약이 깨짐

테스트가 고정 계약 역할을 안 하면, AI diff를 받아도 "맞는지" 검증이 더 어려워진다.

**24. TDD로 진행한다면 어떤 실패 테스트를 먼저 만들어야 안전하다고 느꼈나요?**

**지금 보이는 동작을 고정하는 회귀 테스트**부터다.

- `meter:2.5`, `feet:10`, `yard:1` 등 정상 변환 출력(줄 수, 문자열 형식)
- `:` 없음, 잘못된 숫자, unknown unit 에러 메시지

리팩토링 전에 이걸 RED→GREEN으로 잡아두지 않으면, 구조를 바꾼 뒤 "원래랑 같은지"를 증명할 수 없다. 그 다음에 음수 검증·새 단위·포맷 같은 **아직 없는** 요구를 RED로 추가하는 순서가 안전하다.

**25. 리팩토링 후에도 기존 동작이 유지됐다고 믿으려면 어떤 테스트가 필요하다고 느꼈나요?**

- 정상 입력별 **stdout 전체 스냅샷**(줄 단위, `meter`/`feet`/`yard` 표기, `=` 양쪽 형식)
- 잘못된 형식·숫자·unknown unit 시 **에러 메시지 전문**과 종료 방식(지금은 `return`, exit code 없음)
- feet↔yard 등 **변환 수치**가 meter 기준으로 일관된지(비율 상수 변경 시 양방향 깨짐 검출)
- 리팩토링 후에도 위 테스트가 **구현 세부(클래스 이름, 파일 수)와 무관하게** 통과하는지

CLI 계약 테스트 + 분리된 변환 단위 테스트 둘 다 있어야, "구조만 바꿨다"고 말할 수 있다.
