## 1. 주제 (한 문장)

**단위·비율을 바꿀 때마다 여러 군데를 같이 고치지 않아도 되고, 수정 후 다른 단위 결과가 깨졌는지 자동으로 잡히게 만드는 것.**

> 솔루션은 이 문장에 넣지 않는다. (예: "클래스 N개", "JSON 설정", "JSON 출력" 등 구현 방식은 PRD 범위 밖.)

---

## 2. 배경 — 진짜 문제 vs 표면 문제

### 진짜 문제 (한 문장)

단위 인식, 비율 환산, 결과 출력, 입력 검증이 `main()` 한 함수에 붙어 있어 단위나 비율을 하나 바꿀 때마다 여러 위치를 같이 고쳐야 하고, 자동으로 고정할 검증이 없어 수정 후 다른 단위 결과가 틀어졌는지 매번 수동 실행과 눈으로만 확인해야 하는 상태다.

### 표면 문제 (잘못된 정의)

README의 추가 요구사항(신규 단위, 출력 포맷 분기, 설정에서 비율 로드, 런타임 단위 등록)을 **"기능을 하나씩 붙이는 구현 과제"**로만 정의하고, 그때마다 `main()` 안 분기·출력·비율을 계속 늘리는 방향으로 프로젝트를 잡는 것.

### Mom Test 증거

| # | 증거 |
|---|------|
| 1 | inch 하나 넣으려면 최소 세 군데를 건드린다: `elif` 분기(16–24행), meter 환산(18–21행), 출력 블록(26–32행) |
| 2 | feet 쪽 `elif`만 고치다가 출력의 `in_feet` 곱셈을 안 맞추면, 입력은 feet인데 출력만 틀어지는 식의 불일치가 난다 |
| 3 | 자동 테스트가 없으면 `python UnitConverter.py`로 `meter:2.5`, `feet:10`, 잘못된 입력 등을 직접 넣어봐야 한다 |

## 3. R-G-I-O

| 구분 | 내용 |
|------|------|
| **Role** | `UnitConverter.py`를 인수받아 단위 추가, 입력 검증, 설정 로드, 동적 단위 등록, 출력 포맷 선택 등을 붙여야 하는 **개발자/유지보수자**. CLI를 쓰는 최종 사용자가 아니다. `main()` 한 함수에 몰린 로직을 읽고, 여러 군데를 맞춰 수정하고, 수정 후 깨짐 여부를 확인할 책임이 있다. |
| **Goal** | 단위/비율 변경 시 **한 곳만** 고치면 되게 하고, **자동 테스트**로 회귀를 잡아 수동 실행·눈 확인 의존을 줄이는 것 |
| **Input** | Mom Test에서 드러난 `main()` 혼재 구조(단위 분기 16–24행, meter 환산 18–21행, 출력 26–32행), README 기본·품질·추가 요구사항, 기존 비율 (`1 meter = 3.28084 feet`, `1 meter = 1.09361 yard`) |
| **Output** | 단위 추가·비율 수정 시 **수정 지점이 명확한** 코드 구조, **기존 동작과 에러 메시지를 고정하는** 테스트, 그 테스트를 통과한 리팩토링·기능 확장 결과 |

## 4. 성공 기준

Mom Test 증거와 1:1로 연결한다.

### SC-1. 단위 추가 시 수정 지점이 한 흐름으로 모인다

- **연결 증거:** inch 추가 시 elif · meter 환산 · 출력 3곳 수정
- **성공 조건:** 새 단위(예: inch) 추가 시 `elif`·출력 블록·비율 상수를 각각 따로 늘리지 않고, 단위/비율 정의 **한 경로**만 바꿔도 인식·환산·출력이 맞는다.

### SC-2. 입력 분기와 출력 계산이 어긋나지 않는다

- **연결 증거:** feet `elif`만 수정하고 출력 `in_feet`을 안 맞추면 불일치
- **성공 조건:** feet(또는 임의 단위) 비율을 바꿔도 입력 단위 → meter → 다른 단위 결과가 **같은 비율 정의**에서 나온다. 한쪽만 수정하면 테스트가 실패한다.

### SC-3. 수동 실행 없이 회귀를 잡을 수 있다

- **연결 증거:** 자동 테스트 없이 `python UnitConverter.py`로 수동 확인
- **성공 조건:** `meter:2.5`, `feet:10`, 잘못된 형식, 없는 단위 등 Mom Test에서 손으로 확인하던 케이스가 테스트로 고정되고, 리팩토링·단위 추가 후 **한 번의 테스트 실행**으로 다른 단위 결과 틀림을 알 수 있다.

## 5. 범위 — README 요구사항 (기능)

[README.md](../README.md)의 요구사항은 **본 PRD의 기능 범위**이다. 구현 순서는 SC-1~3을 만족하는 구조·테스트를 먼저 확보한 뒤 진행한다.

### 5.1 기본 기능

- 입력 형식: `단위:값` (예: `meter:2.5`)
- 지원 단위: meter, feet, yard (확장 가능)
- 입력값을 다른 모든 등록 단위로 변환해 출력
- 비율: `1 meter = 3.28084 feet`, `1 meter = 1.09361 yard` (feet/yard 간 비율은 meter 기준)

### 5.2 품질·검증

- OCP를 만족하는 설계
- SRP를 만족하는 클래스 구성
- 입력 검증: 음수, 잘못된 형식, 없는 단위
- 각 단위 간 변환 정확도·검증 로직을 테스트 코드로 검증

### 5.3 추가 기능

| 기능 | 설명 |
|------|------|
| 설정 외부화 | 변환 비율을 외부 설정 파일(JSON/YAML)에서 로드 |
| 동적 단위 등록 | 런타임에 `1 cubit = 0.4572 meter` 형태로 단위·비율 등록 및 사용 |
| 출력 포맷 선택 | JSON / CSV / 표(table) 형태 출력 |

## 6. 하지 않을 것 (Out of Scope — 표면 문제)

이번 프로젝트에서 **의도적으로 하지 않는** 접근:

- inch 등 단위를 **elif + 출력 print + 상수** 세 군데에 복붙하는 방식으로만 추가하기
- JSON/CSV/표 출력·설정 파일·동적 등록을 **`main()` 분기와 `print`에 직접** 얹기
- "기능은 다 붙였다"고 보고 **자동 테스트 없이** `python UnitConverter.py` 수동 확인으로만 마무리하기
- OCP/SRP를 **주석이나 클래스 이름만**으로 충족했다고 보고, **변경 지점 수·회귀 검증**은 그대로 두기
- README 기능 목록을 `main()`에 **순차로 쌓는 것**을 프로젝트 목표로 삼기
